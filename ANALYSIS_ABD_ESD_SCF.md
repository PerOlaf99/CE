# Analysis: ESD / RSD / ABD / SCF container relationships on the MB1000 M13 plate

Status: FINAL (plate-wide, all 96 wells, 2026-09-17). Scripts: `compare_traces.py`,
`best_basecaller/cimarron_basecaller/abd_io.py`.

## What each container actually holds (verified empirically)

| Container | Generated by | Contents |
|---|---|---|
| `*.esd`  | Cimarron DLL | **No trace** (checked: zero channel records, zero correlation with any trace). Just the analysis record: `sequence`, `peak_positions` (absolute RSD scan indices, first base 1992-2216 per run), qualities, PLOC/PBAS. The "truth" reference used everywhere, but it stores NO signal. |
| `*.rsd`  | DLL | Raw full-length trace, one record per channel. This is the axis on which ESD `peak_positions` is expressed (`INT4` records at RSD scan indices). Int16 reconstruction of the float signal. |
| `*.abd` | MegaBACE/Amersham export (ABIF) | DATA1-4: int16 raw trace, same full axis as RSD (scaled slightly differently), channel order **[C,A,G,T]** (dye/base-order calibration, NOT genomic ACGT). DATA9-12: int16 **processed/cropped** trace (~7.2-7.7k samples) cover only the called signal region. PLOC2/PBAS2: DLL's own peak positions and base string expressed in the **processed** axis. |
| `*.scf` | MegaBACE export | Same processed,cropped trace as ABD DATA9-12, same axis. `peak_indices` == ABD `PLOC2`. Columns already `A,C,G,T` order. |

ESD peak_positions sit on the *raw* RSD axis; the cropped containers (SCF, ABD
DATA9-12) start at the first real base, so their local peak 0 is at scan ~0
and maps to the ESD axis by adding a per-run offset:

```
offset = ESD.peak_positions[0] - PLOC2[0]   (== peak_indices[0] for SCF)
```

## ABIF quirks decoded for the .abd files

- File magic `ABIF`. The record-directory file offset lives at **`raw[26:30]`**
  (not the published spec's `raw[24:28]`); with the public offset the directory
  is mis-pointed/dead. `raw[16:20]` holds the element count.
- Only the trace and basecall records (`DATA*`, `PLOC*\`, `PBAS*`) have valid,
  in-file data offsets. Auxiliary records (AEPt, ASPt, LANE, SMPL, DYE, MCHN,
  FWO_1, ...) contain garbage/corrupt `dataOffset` values (frequently pointing
  at other records) and must be skipped or the file is mis-read.
- Traces are big-endian int16 (`etype 4`, `esize 2`). Basecalls: PBAS2 ASCII,
  PLOC2 int16.
- Channel order constant on this plate: `DEDET`-style **[C, A, G, T]** =
  column0=C, column1=A, column2=G, column3=T (variant). Verified against RSD
  and SCF by cross-correlation on every well.

## Consistency checks (all 96 wells)

- Corr(RSD_trace, ABD DATA1-4) and Corr(ABD DATA9-12, SCF_trace): **> 0.9999** everywhere.
- `off_abd == off_scf` on **96/96** wells (per-run crop offsets 1801-2216).
- Our caller (`track_bases`, position mode) run on ABD-raw ≈ run on RSD
  (same signal, different int16 rounding): metrics match or nearly match on all wells.
- ABD-proc and SCF are the *same trace*: our pipeline produces identical
  metrics on **95/96** wells (G01 differs by 0.1 pp).

## Whole-plate result (our `track_bases` on each container vs ESD truth)

| Container | recall (mean / min) | precision (mean / min) | seq. id (mean) |
|---|---|---|---|
| RSD (raw axis, offset 0)        | 86.09 / 42.5 | 80.42 / 41.5 | 96.62 |
| ABD-raw (DATA1-4, offset 0)     | 86.05 / 42.6 | 80.33 / 41.6 | 96.60 |
| ABD-proc (DATA9-12 + crop off)  | **99.49 / 96.8** | 87.17 / 81.0 | 93.35 |
| SCF (cropped + crop off)        | **99.49 / 96.8** | 87.17 / 81.0 | 93.35 |

- "dv_recall" (our calls vs the container's OWN DLL peaks PLOC2/`peak_indices`,
  same cropped axis): mean **99.49**, min **96.8** -- identical to the recall-vs-ESD
  numbers, i.e. on the cropped axis our caller reproduces the DLL's own calls
  but recovers MORE bases than ESD's reported peak list.
- This comparison uses our caller in **position mode** (`auto_trim=False`),
  called against the *full* trace. The big gap between raw and cropped recall
  is not a caller problem: the DLL itself *trims* the signal to the base-bearing
  region on the processed axis, then calls; a raw untrimmed trace contains
  far more peaks than ESD enumerates, dragging down recall/precision.
  Matching the DLL end-to-end = apply our `auto_trim` / `trim "fit then cut"`
  first, then call; on the retained region we agree with the DLL's peaks.

## Migration summary

- New: `abd_io.py` (ABIF .abd reader) exposing the same interface as
  `rsd_io.py`/`scf_io.py`: `read_abd(path)` -> trace_raw, trace_processed,
  bases, peak_positions + `to_acgt_trace()` reorder helper. Repairs done in
  `99_archive/abd_repair.py` earlier.
- New: `compare_traces.py` -- reusable, parallelized (8 workers) harness that
  runs our caller over any set of wells on RSD/ABD/SCF and scores vs ESD +
  per-container own peaks. Runs: `python3 compare_traces.py` (all 96),
  `compare_traces.py A` (row), `compare_traces.py A01 B09` (explicit wells).
- ESD remains the canonical "truth" artifact (sequence + absolute peak_positions,
  RSD axis). SCF/ABD-proc give the same-drop copy the DLL actually called from;
  RSD/ABD-raw give the full untrimmed signal ESD's own coordinates live on.
